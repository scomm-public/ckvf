# Profile: pepper-oprf

**Status:** SComm.AI Draft 0.1 profile  
**Normative for implementations that claim this profile**  
**Not an IETF standard**

This profile defines the unlock methods `password-oprf-argon2id` and
`recovery-code-oprf-argon2id`. They wrap the VEK under a KEK that needs both
the user's secret and one online evaluation by the vault host. Someone who
steals the container, or the whole vault host database, cannot run an
offline dictionary attack: every guess costs a rate-limited request to a key
that is not in the database.

Core data model, cryptography, and operations remain in [SPEC.md](../SPEC.md).

## 1. Slot

```json
{
  "slot_id": "<base64url 16>",
  "method": "password-oprf-argon2id",
  "created_at": "2026-09-27T00:00:00Z",
  "kdf": {
    "alg": "Argon2id",
    "salt": "<base64url ≥ 16>",
    "m": 65536,
    "t": 3,
    "p": 4,
    "key_length": 32
  },
  "oprf": {
    "suite": "ristretto255-SHA512",
    "mode": "poprf",
    "kid": "<host key id>",
    "public_key": "<base64url 32>"
  },
  "wrap": { "alg": "A256GCM", "iv": "…", "ciphertext": "…", "tag": "…" }
}
```

`kdf.m` MUST be at least 65536 and `kdf.t` at least 3. The general limits of
SPEC.md §6.5 also apply. The wrap AAD is SPEC.md §6.3 with this slot's
`method`.

## 2. Derivation

The OPRF is RFC 9497 POPRF (mode `0x02`), suite `ristretto255-SHA512`.

```text
secret  = UTF-8 of the password (NFC), or the canonical recovery code (§4)
info    = "CKVF-pepper-v1" || 0x00 || vault_id || 0x00 || slot_id
rwd     = POPRF.Finalize(secret, blind, evaluation, proof, info)   ; 64 octets
KEK     = Argon2id(password = rwd || secret, salt = kdf.salt,
                   m = kdf.m, t = kdf.t, p = kdf.p, tagLength = 32)
```

`vault_id` and `slot_id` are the base64url strings from the container, as
ASCII. The client MUST verify the POPRF proof against `oprf.public_key`
before Finalize. A proof that does not verify fails the unlock the same way
a wrong password would, and the client SHOULD tell the user the host
returned an invalid evaluation.

Because `info` contains `vault_id` and `slot_id`, an evaluation obtained for
one vault is useless for guessing the secret of another. The host can
therefore rate-limit by `vault_id` without trusting the caller.

## 3. Host evaluation

`POST /v1/pw-oprf/evaluate` on the vault host
([vault-host.md](vault-host.md)):

```json
{ "vault_id": "…", "slot_id": "…", "kid": "…", "blind": "<base64url 32>" }
```

returns

```json
{ "kid": "…", "evaluation": "<base64url 32>", "proof": "<base64url 64>" }
```

The host:

- keeps the POPRF private key outside its database (KMS or process
  environment) and separate from any other OPRF key;
- recomputes `info` from `vault_id` and `slot_id` itself;
- returns `404 unknown_vault` for a `vault_id` it does not hold;
- rate-limits per `vault_id` (RECOMMENDED 20 per 24 hours) and per client
  address, and alerts on sustained limits;
- requires the same authorization as reading the container (vault-host.md);
- never learns whether the unlock succeeded.

`GET /v1/pw-oprf/keys` lists the POPRF public keys:

```json
{
  "suite": "ristretto255-SHA512",
  "mode": "poprf",
  "current_kid": "…",
  "keys": [{ "kid": "…", "public_key": "<base64url 32>", "status": "current" }]
}
```

`status` is `current` or `retired`. New slots pin `current_kid`. A client
that sees its slot's `kid` as `retired` rewraps after unlock (§5).

## 4. Secrets

Passwords SHOULD be generated by the application with at least 100 bits of
entropy. User-chosen passwords are allowed; the pepper is what makes a weak
one survive a database leak.

A recovery code is 26 characters of RFC 4648 Base32 (130 bits), shown in
groups. The canonical form removes spaces and hyphens and uppercases.
Implementations MUST derive from the canonical form.

## 5. Key rotation

The host publishes each POPRF public key with its `kid` and keeps retired
keys available for evaluation until every slot using them has been
rewrapped. On a successful unlock with an old `kid`, the client SHOULD
rewrap the slot under the current `kid` (new salt, new wrap IV, same VEK)
and commit a generation.

Losing the POPRF private key makes every slot that uses it permanently
unrecoverable. Hosts MUST back the key up with a documented restore
procedure. Device slots keep working without the host.

## 6. Merge

Slots of these methods merge like any other slot (SPEC.md §12.7). A slot
whose `oprf.kid` differs from the other side's copy of the same `slot_id` is
a rewrap; the newer generation wins.

## 7. Test vectors

`test-vectors/pepper-oprf/` holds deterministic POPRF transcripts
(`poprf.json`: key, `info`, blind, evaluation, proof, Finalize output) and
containers for both methods and for `device-wrap-a256gcm`, with negative
cases for a wrong pepper, an Argon2id floor violation, a missing `oprf`
object, and a device slot carrying `kdf`.
